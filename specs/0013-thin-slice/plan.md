## Approach

M3 is the first vertical slice: a request travels from an HTTP endpoint through YAF's own dispatcher and pipeline into a handler, an aggregate is stored by a repository and a unit of work on PostgreSQL, and the result comes back as a response or a problem document. It adds seven packages (`YAF.Application`, `YAF.Infrastructure` (empty for now), `YAF.Persistence.EfCore`, `YAF.Persistence.EfCore.PostgreSql`, `YAF.Http`, `YAF.Http.MinimalApis`, `YAF.Testing.Integration`), four source generators in the `Analyzers` project (error registry, handler registry, memento data classes, endpoint discovery), the fakes, builders and rules of `YAF.Testing`, and the first part of the sample (`Catalog` with `Session` create and get). The work is 91 tickets in five lanes that can run side by side: application (T7–T25), analyzers (T5, T26–T29, T33–T36, T57), persistence (T30–T51), HTTP (T48, T52–T56), testing (T58–T71), then the sample (T72–T81), docs (T82–T89) and the specification and skill updates (T90, T91).

What shapes the plan, each checked by a probe on SDK 11.0.100 ([research](./research.md)):

- **`YAF.Application` takes no package.** In .NET 11 the `Microsoft.Extensions` abstractions (DI, logging, options, hosting, diagnostics) are part of `Microsoft.NETCore.App`; an explicit reference is warning NU1510, an error here (research §3). The only new third-party packages are EF Core and Npgsql for persistence, and Testcontainers, the ASP.NET Core test host and xUnit's extensibility package for `YAF.Testing.Integration`, each on ADR-0003's allow-list for its package (research §2).
- **Analyzer exceptions are planned, not discovered.** A skeleton of `YAF.Application`'s public types set off five rules on names and shapes that `04` prescribes: CA1040 on the four marker interfaces, CA1711 on `RequestDelegate<TResult>` and `IDomainEventHandler<TEvent>`, CA1716 on the parameter `next`, CA1724 on `Principal` (research §4). T1 adds the scoped `.editorconfig` sections before the files exist, so that the tickets that write the code stay tier medium (as T2 of plan 0009). The rest of what the probe found is avoided in code.
- **`TypedIdConverter<TId>` calls a helper.** An EF value converter is an expression tree, and an expression tree cannot name a static abstract member (CS8927). The converter keeps the generic shape of `05` §1 and calls a private static method that calls `TId.From` (research §5).
- **Multi-value value objects are complex types with every component named.** `Money`'s properties are get-only, so EF does not map them by convention and model building fails; naming each component works, also for `Period?` with its private constructor (research §6). The convention of T38 does that for the shipped multi-value value objects.
- **A generated data class holds its children twice.** EF navigations need an entity type, not an interface. The generator emits a mapped `List<SeatData> SeatRows` and implements `IList<Seat.IMemento> Seats` explicitly as a view over it (research §7), with the name the `yaf-persistence` skill already uses.
- **`ResultFactory` needs no generator.** `03` §1 says "source-generated per closed result type, no reflection". Generated code in an application assembly can reach `YAF.Core` only through a registration, which is static mutable state (hard rule 7). `Result` and `Result<T>` instead implement an internal interface that creates a failure of their own type; `ResultFactory.Failure<TResult>` asks `default(TResult)` for it. No reflection, AOT-compatible, same public signature (deviation 5).
- **Generated registries are found through one assembly attribute each.** `AddHandlersFrom<TMarker>()` reads `[assembly: YafHandlers(typeof(…))]`, `MapEndpoints<TMarker>()` reads `[assembly: YafEndpoints(typeof(…))]`, and `IErrorCatalogProvider` reads `[assembly: YafService("catalog", typeof(…))]` from the loaded assemblies. The generator emits attribute and registry; no type scanning happens at run time (`04` §2, `03` §2.1, `08` §2).

### Alternatives rejected

| Alternative | Why not |
|---|---|
| A source-generated `ResultFactory` registered by a module initializer | Static mutable state in `YAF.Core` (hard rule 7); the internal-interface form does the same with no generation (deviation 5) |
| Pipeline builder that takes the built-in middleware as type arguments, `InsertAfter<ValidationMiddleware, MyMiddleware>()` as `04` §3 writes it | Open generic types cannot be type arguments in C#; every middleware that applies to all requests is open generic (Q4) |
| Non-generic step marker classes for the built-in middleware | They would let `InsertAfter<ValidationMiddleware, …>` compile for the anchor, but a service's own all-request middleware is still open generic, so the `Type` overloads are needed anyway; two ways to name a step |
| `EFCore.NamingConventions` for snake_case | Not on ADR-0003's allow-list; a convention of a few lines in `YAF.Persistence.EfCore.PostgreSql`, where `01` §2.1 places snake_case naming |
| Mapping `Money` and `Period` with value converters to JSON or one text column | `05` §1 prescribes complex types, one column per component; probe C shows complex types work with named components |
| Value converters for an app's own value objects found by a marker interface (`ISingleValueObject<TSelf, TValue>`) | A new public contract `02` and `05` do not have. The convention covers the shipped value objects; an app maps its own in its entity configuration (decision log) |
| One build ticket per package that also pins its third-party packages | Every skeleton ticket would touch `Directory.Packages.props` (tier high, shared); T2 pins them all once |
| Testing the two-assemblies case of `03` §5 item 3 with assemblies compiled in memory | The registry is emitted by the generator at build time; two small fixture projects under `tests/Fixtures/` give the real thing and serve both halves (T25, T66) |
| Letting the provider read every assembly loaded in the test process while the duplicate fixtures are loaded; a test project of its own for the duplicate case; an `AssemblyLoadContext` per test | The first makes `tests/Application.Tests` order-dependent (every later host start would see the duplicate); the other two add a project or loader code for one test. Chosen: the provider and the startup check read their assemblies from an internal `IErrorCatalogAssemblySource`, which T25's test replaces with one that returns the two fixtures, so the fixtures are never loaded into the shared test process (the owner's choice) |
| The exit test "two concurrent commands change only a child" through the sample's HTTP API | Row M3 builds only create and get for `Session`; the component test of T51 drives two units of work deterministically against PostgreSQL. The sample's `SeatLimitConcurrencyTests` (`16` §3) come with `ReserveSeat` |
| Region markers added by the docs tickets | The docs tickets would change compiled files; the tickets that write the tests add the regions (as in plan 0009) |

## Schema and migration plan

The framework adds no table in M3. The sample's first migration `InitialCatalog` creates `sessions` (id, tenant, version, the four stamps, title, capacity, status, format, price amount and currency, schedule start and end) with snake_case names (T79). Row-level security on `sessions` is added by M4 in a migration of its own (`05` §4).

10. **The conventions map only the shipped value objects** (`05` §1).

14. **`IErrorCatalogProvider` lists YAF's own catalogues** (`03` §2.1 reads "the loaded assemblies that declare `[assembly: YafService("catalog")]`").
