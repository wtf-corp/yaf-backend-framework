## Approach

ADR-0029 already describes the loop: pick ready tickets, one implementer per ticket in a worktree, a separate review, a pull request, gates, automatic merge for tier low and medium, a human for tier high, two fix rounds, then `needs-human`. Run on 2026-11-19 with the owner at the keyboard, it needed the owner in eight places where the decision does not ask for a person. Each is verified in [`research.md`](./research.md) and closed by the smallest change.

### Who does what in an unattended run

Decided here and recorded in the decision log.

- **The orchestrator is one Claude Code session at the repository root under `/loop`**, self-paced (research §5). Each tick runs the skill's loop once. The state is on GitHub and in git: the Project, the open pull requests with their checks, the review summaries, marker comments on the tickets, and `git worktree list`. A tick needs nothing from the tick before, so a restarted session picks up where the last one stopped.
- **Implementers are Claude Code subagents** of that session, started in the background from the kit's `implementer` and `implementer-high` definitions, which already carry `isolation: worktree`. This is what ADR-0029 §1 decided and what ran on 2026-11-19. The worktrees are under `.claude/worktrees/`, which is ignored by git and inside the project.
- **Orca is where the session runs and is watched**: a terminal that stays open, next to the worktrees it shows. Orca workers are not used for implementers (the owner's decision: "Subagents, Orca as host"). Orca does not watch GitHub, so the loop would be needed in either case.
- **The owner** approves what the policy reserves: tier-high pull requests, flagged plans, specs. An approval is the last step: with T2 and T3 it merges. The owner is asked by a review request: GitHub's own for the code owners when a pull request on a code-owned path opens, and the factory's once the model review has passed (T4). The session adds a desktop notification (T14). The owner also pushes the branch of a ticket that changes a workflow file.
- **Every ticket's pull request targets `main`.** The gates run only for `main` and `next`, so a pull request stacked on another ticket's branch would get no checks. In an unattended run a ticket that depends on an open one waits until that one has merged; nothing is stacked. The cost is time: T7 waits for T5 to merge, and T8 for T6 and T7.

### The approval check covers a tier-high plan (T1)

The owner's decision of 2026-11-19: "Require approval in the gate".

Today `gates.mjs` (lines 136 to 139) computes the verdict of `factory/human-approval` with `humanApprovalVerdict(kind === 'plan' ? 'low' : tier, approvingHuman(reviews, { author, headSha, isHuman }))` and gives every plan pull request the title "plan pull request: see factory/plan-gate". So a plan in tier high passes the check with nobody's approval, and an unflagged one passes `factory/plan-gate` too: a required check that is named for the human approval does not demand one (research §1).

- `human-approval.mjs` gains `approvalTier(kind, tier)`: for a plan, `high` when the tier is high and `low` otherwise; for every other kind the tier itself.
- `gates.mjs` passes `approvalTier(kind, tier)` to `humanApprovalVerdict` in place of the inline expression, and keeps the title "plan pull request: see factory/plan-gate" only for a plan that is not tier high; a tier-high plan gets the verdict's own title ("tier high: waiting for an approving review …" or "approved by …"). `approvingHuman` is called as now. Nothing else in the gates changes: `factory/plan-gate` still decides flagged plans, and a plan in tier low or medium is as before.
- Tests in `tests/human-approval.test.mjs`, a new file, which T4 extends.
- No open ticket of plan 0002 touches `gates.mjs` or `human-approval.mjs` (checked against the `Touches` of 0002's ten rows; its T9 changes the policy, a kit test and prose).
- The gates run from the base branch, so the change holds for pull requests whose gates run after it has merged; an open tier-high plan turns red at its next gates run until it is approved.

### The arming decision (T2) and the workflow (T3)

T2, `docs/spec/factory/.github/factory/automerge.mjs`, new, with the decision as a pure function and the command part below it, the way `post-review.mjs` is built.

`armDecision({ labels, draft, kind, approver, planGate, armed, paused, gatesConclusion })` → `{ action, reason }`, where `action` is `arm`, `disarm` or `none`:

- The tier is the highest `tier:*` label present: `tier:high` beats `tier:medium` beats `tier:low`. A draft, or no tier label: `none`.
- `needs-human`: never armed. Tier low or medium without it: `arm`, as today.
- Tier high qualifies only when `approver` is set, and for kind `plan` only when `planGate` is also `success`. Qualified: `arm`.
- A `needs-human` or tier-high pull request that does not qualify: `disarm` when `armed`, else `none`. This also disarms a pull request someone armed by hand before it was approved; that is intended.
- `arm` on a pull request that is already armed is `none`.
- Arming needs a factory that is not paused and a gates run that concluded `success`: otherwise an `arm` becomes `none`, with the reason. Disarming needs neither: an unapproved tier-high pull request that is armed is disarmed while the factory is paused and after a failed gates run as well.

What the command part hands in, all read through the API with the app's token:

- `approver`: `approvingHuman(reviews, { author, headSha, isHuman })` from `human-approval.mjs` with `makeHumanCheck(policy)`, the same two functions `gates.mjs` uses. It returns a login only for an approving review by a human maintainer of the policy, not the author, given on the head commit. The script does **not** take the check `factory/human-approval` as its proof: until T1 has merged, `gates.mjs` passes that check for every plan pull request, whatever its tier, and after it the script and the check are two readings of the same reviews, made in two places (research §1).
- `kind`: `prKind` over the pull request's changed files.
- `planGate`: the conclusion of the newest `factory/plan-gate` check run on the head commit that the gates' app reported (`app.slug` equal to `bots.gates` of the policy without `[bot]`); a check of that name from any other app is ignored. For an unflagged plan in tier high this is `success` and the human's approval is still required by the rule above; for a flagged one it is `success` only once `gates.mjs` has seen the approval itself.
- `armed`: whether the pull request's `auto_merge` is set. `paused` and `gatesConclusion` come from the workflow: the pause variable and the conclusion of the gates run that started it.

What it does: `arm` → `gh pr merge <n> --auto --squash --match-head-commit <sha>`, with the head commit the decision was made on, so that a push in between cannot be armed by a decision about the commit before it (research §1; that the flag binds an automatic merge as it binds a direct one is [assumed], and T3's trial shows it). `disarm` → `gh pr merge <n> --disable-auto`. It prints the decision and its reason.

The kit README is changed by T3, not by T2, because its sentences become true only when the workflow runs the script. The README is not a workflow path and the app could push it; it is the workflow files in the same branch that make the push the owner's. `docs/spec/factory/README.md`: "How a ticket flows" step 8, the line for the workflow under "What is in it" and one sentence in "Running the orchestrator" say that a tier-high pull request merges once a maintainer has approved its head commit, that an approval is therefore the decision to merge, and that the workflow takes automatic merge off a tier-high pull request that is not approved, paused or not.

T3, both copies of `factory-automerge.yml` (the kit's and the installed one), kept to what the script needs:

- The job's `if:` loses `conclusion == 'success'` and keeps `event != 'merge_group'`: the job runs after every gates run, because disarming must.
- The pause step stays as the place the variable is read; the token step loses its `if:`, because a disarm needs the token while the factory is paused too.
- The inline shell of the last step is replaced by a checkout of the default branch (`persist-credentials: false`), `setup-node` (Node 22), and one call of the script, with the pause value and `github.event.workflow_run.conclusion` in its environment; the two actions are pinned to the commits `factory-gates.yml` already uses.
- The job still runs on `workflow_run`, from the default branch, with the app's token, and still checks nothing out from the pull request.

T3 depends on T1 as well as T2, so that tier high is never armed while the required check still passes a tier-high plan by itself. Two tickets for the script and the workflow because T2 can be pushed by the app and T3 cannot (research §9), and because T2 with its tests is near the size limit by itself.

Why this does not loosen the approval. No requirement for merging is removed, and T1 adds one for a plan in tier high: the ruleset still requires `factory/human-approval` from GitHub Actions, a code owner's review on code-owned paths, and every other check. Before, the order for tier high was approve, then merge by hand; now the second step is done by GitHub when the first is complete. The approval is checked twice, in two places: by the arming script, which reads the reviews itself with the policy's human check, and by the required check `factory/human-approval`, which the gates job computes from the same reviews and which, with T1, demands a maintainer's approval of the head commit for every tier-high pull request, plans included. Neither rests on the other's result. And the script works in both directions, so a tier-high pull request is armed only while it is approved: a disabled ruleset releases nothing a human has not approved (research §1). What is lost is the pause between approving and merging; it is deviation 2.

### The review request (T4)

- `human-approval.mjs` gains `reviewersToRequest({ needed, approver, author, requestedUsers, requestedTeams, reviews, headSha, humans })` → logins. Empty when no human is needed, when one has approved, or when a team's review is already requested (the request GitHub makes for the code owners). Otherwise the policy's `humans.logins` without the author, without anyone already requested, and without anyone who has submitted a review of the head commit.
- It is called from `post-review.mjs`, when the review it posts has passed: `needed` is "the pull request has the label `tier:high`, or it is held for a human" (`heldForHuman`, which the poster already computes for a document review). So the factory asks the owner only once the model review has passed on the head commit (the orchestrator's choice, decision log). That is not true of every request: for a pull request on a code-owned path GitHub asks the code owners when it opens, before the model review. An approval given that early is safe: `factory/review` is a required check, so the approval only arms, and nothing merges until the review has passed on that same commit. The poster fetches what it needs itself, through the API: the pull request's labels, the requested reviewers (users and teams) and the reviews. The event file it is given holds only the number and the two commits when the review runs locally (`local-review.mjs` writes it so). Then it posts the request; with `humans.logins` empty it asks `humans.team` as a team reviewer. A failed request is a warning in the log and changes no check.
- It is the place that runs when the review finishes: a check run starts no gates run, so `gates.mjs` would not see the passed review until something else happened to the pull request. It works the same when the reviews are back in CI; there the job has `pull-requests: write`, here the reviewer app has it (research §2).

### What is in flight (T5, T6, T7, T8)

`docs/spec/factory/.github/factory/inflight.mjs`, new.

T5, `nextAction(pr, policy, now)`, pure. Input: labels, draft, kind, whether a human maintainer approved the head commit, the newest check run per name on the head commit (name, status, conclusion, title, start time), the rounds number of the summary comment, whether a references fix was already tried on the ticket, and for the worktree that holds the branch: whether it is locked, and whether its head is ahead of the pull request's. Output `{ action, reason, round, cause }`, the first that applies:

| Order | Condition | Action |
|---|---|---|
| 1 | label `needs-human` | `human` |
| 2 | draft | `none` |
| 3 | no completed `factory/tier` on the head commit | `wait` (the gates have not reported) |
| 4 | kind code, the job `references` failed and no references fix was tried yet | `fix` with the cause `references`: the implementer runs `node .github/scripts/sync-references.mjs` in its worktree and commits the result |
| 4b | `factory/tier`, `ticket`, `size`, `delta` or `guards` failed, or `factory/plan-gate` failed with a title that does not start with "flagged"; or one of the jobs `references` (after a tried fix), `factory-self-test` or `factory/test-evidence` failed | `gate-failed` |
| 5 | `factory/review` or `factory/doc-review` is in progress and started less than 30 minutes ago | `wait` (the review runs) |
| 6 | one of the two is missing on the head commit, or in progress for longer | `review` |
| 7 | one of the two failed | For kind code: `wait` when the worktree is locked (a fix is being written) or ahead (a fix is committed and not pushed); otherwise `fix`, with `round` = the rounds number. For a plan or a spec: `human`, with the reason "a plan or spec fix is attended" |
| 8 | the label `tier:high` without an approval of the head commit, or `factory/human-approval` failed, or `factory/plan-gate` failed "flagged" | `human` |
| 9 | otherwise | `wait` (GitHub merges) |

`gate-failed` is reported and escalated, never worked around (skill, stop conditions). The three jobs are check runs of the gates workflow on the head commit; a failed `factory-self-test` means the kit's own tests fail on the branch, which is the writer's defect and still a person's call here, because the job is not a required check and nothing else would stop the merge. An unattended run runs no fix round on a plan or spec pull request: the planner and the spec writer have no worktree isolation and no `acceptEdits`, so they would edit in the main checkout and stop at prompts. The orchestrator tells the owner, and the fix is made in an attended session, as today (the orchestrator's choice, decision log). A references fix is tried once: the orchestrator marks the try on the ticket (T6), and a second failure is `gate-failed`. A failed build or test job gets no action of its own: there is no `ci.yml` before M0. There is no action for a branch behind `main`: with the strict policy off, GitHub merges a green pull request whatever `main` has gained since (decision log).

T6, `docs/spec/factory/.github/factory/markers.mjs`, new, pure: what the run records on GitHub and how it is read back.

- Three markers, hidden comments on the ticket's issue, written by the orchestrator through `gh issue comment` as the factory app: `<!-- factory:local-review <sha> ready round=<n> -->` or `<!-- factory:local-review <sha> changes-required round=<n> -->` after the code reviewer's verdict on that commit, followed in the same comment by the findings as the reviewer gave them, so that the local loop can be resumed and capped from the record. **The round, defined once:** `round=<n>` is the number of local fix rounds already used on the ticket when the verdict was given: 0 for the first local review, 1 for the review of the first fix, and so on, counted per ticket and not per commit. It is the local loop's count only; the rounds of the pull-request review are counted apart, by `post-review.mjs` in `factory:rounds`. A `changes-required` verdict with `round >= limits.fixRounds` (2 by default: the first review and two fixes have failed) is the end of the local loop: `needs-human`, no further fix; `<!-- factory:awaiting-push <sha> -->`, posted once per commit when the owner has been told that the push is theirs; `<!-- factory:references-fix <sha> -->` when a references fix was handed out for that failing commit.
- `marker(kind, sha, value)` builds the text; `findMarker(comments, kind, sha, author)` finds it, and counts a comment only when its author is the factory bot of the policy, so that a marker someone else writes changes nothing.
- `localReview(comments, sha, author)` → the verdict, the round and the findings text for that commit, and the highest round recorded on the ticket for any commit.
- `reviewSummary(comments, check, authors)` → the rounds number and the body of the comment that carries the review's marker (research §3), counting only a comment whose author is in `authors`. A summary comment written by anyone else does not count: its body goes verbatim to an implementer as findings, and its rounds number decides a fix round.
- A module of its own, so that T5 and T6 share no file and run in parallel.

T7 adds two pure functions to `inflight.mjs`, `parseWorktrees` and `worktreeState`; they are described below with the output they feed.

T8, the command: `node docs/spec/factory/.github/factory/inflight.mjs` prints JSON. It reads only. It is run through the token helper as the factory app, so its trial, V4, runs once the helper's command line exists (0002's T5, #16); the ticket itself needs nothing from plan 0002, and its tests need no token. Its assembly of one pull request's row from what was fetched is an exported pure function, so that the command has a test of its own.

T8 also names the reviewer app where a script can read it. No file a script reads does today: `policy.json` `bots` holds `factory` and `gates`, and the name `yaf-reviewer` is only in a comment of `local-review.mjs` and in `AGENTS.md`. `docs/spec/factory/.github/factory/policy.json` gains `"reviewer": "yaf-reviewer[bot]"` in `bots`, and `policy.schema.json`, whose `bots` object lists its keys and allows no others, gains the property `reviewer`, optional: a repository whose reviews run in CI has no reviewer app, and there the summary is written by the gates bot. The command passes `[bots.reviewer, bots.gates]`, without an absent one, as the `authors` of `reviewSummary`. It is a change to the policy file, which is the owner's to approve (decision log). No kit test and no other script reads the keys of `bots` beyond `bots.gates` in `gates.mjs` and the bots list of the digest [repo], and `policy.json` is also changed by 0002's T8 (#19), in other lines, so T8 waits for it.

- `pullRequests`: every open pull request labelled `factory` or opened by `bots.factory`, each with number, branch, the closed issue, kind, `action`, `reason`, `round`, `fixRounds`, `cause`, and for `fix` the body of the review's summary comment, which holds the findings verbatim (research §3).
- `worktrees`: from `git worktree list --porcelain`, parsed by an exported pure function `parseWorktrees(text)`: path, branch, head, locked or not. For a worktree whose branch has the form `<type>/<issue>-<slug>`, `worktreeState(…)`, pure, gives the first that applies:

  | Condition | State |
  |---|---|
  | the ticket or its pull request has the label `needs-human` | `human` |
  | locked | `working` |
  | the branch's pull request is merged | `remove` |
  | the ticket has no local-review marker for the worktree's head | `local-review` |
  | the marker for the head says `changes-required` | `local-fix`, with the marker's round and findings, and `exhausted` when that round is `limits.fixRounds` or more |
  | the marker says `ready` and the head is not on `origin` | `push-owed`, with `notified` when the ticket has the awaiting-push marker for that head |
  | the head is on `origin` and the branch has no open pull request | `open-pr` |
  | otherwise | `in-flight` (see `pullRequests`) |

- The markers and the review summary are read with the functions of T6. The heads on `origin` come from `git ls-remote --heads origin`.
- `push-owed` normally lasts a moment: the implementer pushes before it reports. When it did not, the orchestrator pushes from the main session, as the app, with `node .github/scripts/factory-token.mjs --app factory -- git -C <worktree> push -u origin <branch>` (the form is on the allowlist, T11). It stays for a ticket that changes `.github/workflows/`, whose push is the owner's.

### A running review is visible (T12)

A local review takes about three minutes. During them the head commit has no review check, which is also the state "review owed", so the next tick would start a second one. `local-review.mjs` therefore reports, before it starts the reviewer, a check run with the review's name on the head commit, `status: in_progress` and the start time, with the reviewer app's token; `post-review.mjs` then reports the completed one, and the newest run of a name counts (kit README, "Verify before relying on it"). Nothing is posted with `--dry-run`. A script that dies in between leaves the check in progress; `nextAction` treats one older than 30 minutes as owed again. A check run was chosen over a marker comment: it sits on the commit it is about, needs no cleanup, and the reviewer app already has Checks write (research §3). The script cannot hold a tested function (it runs on import, research 0002 §6), so what is sent is built by an exported pure function next to `setCheck` in the kit's `lib.mjs`, `inProgressCheck(name, sha, title, now)`, with a unit test, the way 0002's T10 put `withoutToken` where a test can reach it. `local-review.mjs` imports it from the base checkout, as it imports `setCheck`, posts the body, and skips the step when the base branch does not have the function yet. The reading side is tested in T5.

### The helper refuses what is reserved for a human (T9)

After plan 0002 the form agents use is `node .github/scripts/factory-token.mjs --app factory -- gh …`, which no `gh` or `git` deny rule matches (research §7). Twins of 34 rules for the wrapped form in two shells would be 68 more text patterns. The helper is the one place every such command passes through, and it sees arguments, not text:

- `factory-token.mjs` exports `refusedCommand(command, args)` → a message or `null`, called before anything is minted; a refusal exits 2.
- Refused, mirroring the deny rules of the settings: `gh pr merge`; `gh pr review` with `--approve` or `-a`; `gh release`, `gh label`, `gh repo edit`, `gh secret`, `gh variable set`, `gh variable delete`, `gh workflow disable`; `gh pr edit` and `gh issue edit` naming `guard-change`, `major-release` or `size-accepted`; `gh api` with an argument that names a pull request's `reviews` or `merge`, `merge-queue`, `rulesets`, a branch `protection`, `environments`, or `labels` together with one of the three labels; `git tag`; `git push` with `--force…` or `-f`, or with a refspec whose destination is `main`, `next` or `stable`. Global options before the subcommand (`git -C <dir>`, `git -c <k=v>`) are skipped, so `git -C . push origin main` is refused, which the text rule does not catch (kit README checklist 7).
- It holds for the Bash tool, the PowerShell tool and a terminal alike.
- What it is not: a boundary. `-- bash -c "…"` or a script run with `node` is not looked into. The controls that hold are the app's permissions and the ruleset (kit README checklist 7); the helper stops the accident, and says so in its message.

### The skill (T13)

`docs/spec/agents/skills/yaf-orchestrating-work/SKILL.md`, tool-neutral as the bundle requires (`docs/spec/agents/README.md` §3):

- "The loop", step 2 gains the actions of U4 in one table: review owed → run the review; the references out of step → one fix round that regenerates them; review failed on a ticket's pull request → a fix round for its implementer, with the findings verbatim and the round number; review failed on a plan or spec pull request → in an unattended run nothing but telling the owner: those fixes are made in a session a person attends; waiting for a human → nothing, list it; a failed gate → report and `needs-human`. The label goes on the pull request, where the gates and the merge workflow read it, and on the ticket. Where a script gives the next action, the orchestrator takes it from the script (`.github/factory/inflight.mjs`).
- Step 3: in an unattended run nothing is stacked. Every pull request targets the protected branch, because the gates run only there; a ticket that depends on an open one waits until it has merged. The "stacked" option stays for a run a person attends.
- Step 4 changes: the orchestrator creates no worktree and no branch. It starts the implementer, whose tooling gives it a worktree of its own; the brief names the branch to create there and its base. The brief's line `Worktree: <path>` goes, and the report gains the worktree's path, which the orchestrator needs for rule 8.
- Step 5 gains the record: after the code reviewer's verdict the orchestrator writes it on the ticket as a marker comment naming the commit, with the round and the findings, so that a later run knows whether a finished worktree was reviewed, which round is next and what to hand to the implementer. The limit of rule 10 is counted from that record.
- A new short section, "Worktrees": one per ticket, found again by the branch it holds; never created or entered by the orchestrator for writing. A fix round goes to the same writer when it can be resumed; otherwise to a new one, whose brief says to check out the pushed branch, after the orchestrator has removed the earlier worktree, which it may do only when that worktree is clean and its head equals the pushed branch. After the merge: unlock if a lock was left behind, remove the worktree, delete the ticket's local branch and the branch the tool made.
- A new rule: a ticket that needs a ticket of **another plan** that is still open cannot say so in its `Depends on`, which takes keys of its own plan. When a plan's tickets are created, the orchestrator labels each such ticket `blocked` and comments which issues it waits for, taken from the plan's "Tickets" section; it removes the label when those issues have closed. Rule 4 already keeps a `blocked` ticket from being picked, and the status script leaves it out of `Ready`.
- A new rule: the agents' identity may lack the permission to push some paths (here: workflow files). A ticket whose `touches` name such a path is started like any other; its implementer commits and reports without pushing; the orchestrator re-runs the verification and the local review, records the verdict, then tells the owner the branch and the worktree, marks on the ticket that it did, and opens the pull request once the branch is on the remote. Every fix round on it ends the same way. It never pushes with a person's login.
- Rule 12 and "Stop conditions": everything that is left waiting for a human no longer ends an unattended run, and neither does a `needs-human` that blocks the rest. The orchestrator reports it, tells the owner once per change of that list, picks up nothing, and keeps checking at the longest interval; it resumes by itself when the owner has acted. The pause, the end of a milestone, a wrong guard and a repeated infrastructure failure still end it. A run a person attends stops and reports as before.
- Anti-pattern row "Merging a green pull request, or enabling auto-merge yourself" is reworded: the workflow arms every tier, tier high after the approval.
- `docs/spec/factory/README.md`, "Running the orchestrator": the sentence on what the session does per ticket follows the new step 4, and the start prompt for an attended run keeps its "Stop at the end of the milestone or at the first needs-human" with one sentence that an unattended run (`/loop /factory-run`) waits instead.

### The command (T14)

`docs/spec/factory/.claude/commands/factory-run.md`, copied verbatim to `.claude/commands/factory-run.md` by one new entry in `VERBATIM` of `.github/scripts/sync-references.mjs`. It is a command of the kit and not a skill of the bundle because it is specific to Claude Code (`docs/spec/agents/README.md` §3: skills hold "no tool-specific instructions"). It must be invocable by Claude, so it has no `disable-model-invocation` (research §5).

Front matter: a description, and `allowed-tools` with the orchestrator's own commands, each for Bash and PowerShell. The grant lasts for the turn the command starts (research §7):

- `gh variable get FACTORY_PAUSED` (the one read with the person's login, research §10);
- through the helper as the factory app: `node docs/spec/factory/.github/factory/inflight.mjs`, `node docs/spec/factory/.github/factory/status.mjs set *`, `gh project item-list *`, `gh pr create *`, `gh pr comment *`, `gh issue comment *`, `gh issue edit * --add-label needs-human`, `gh issue edit * --add-label blocked`, `gh issue edit * --remove-label blocked`;
- through the helper as the reviewer app: `node .github/scripts/local-review.mjs *`;
- `git worktree unlock *`, `git worktree remove *`, `git branch -D *`.

Body, one tick, in this order; the skill is the instruction and the command adds only how a tick runs here:

1. Load `yaf-orchestrating-work`. Read the pause variable. Paused: tell the owner, end the loop.
2. Run the in-flight command.
   - For each pull request: `review` → start the local review in the background; `fix` → resume the implementer of that pull request, or start a new one, with the summary comment verbatim and "round N of M"; for the cause `references`, with the one instruction to regenerate and commit, after posting the references-fix marker; `gate-failed` → comment, and `needs-human` on the pull request and on the ticket; `human` → collect for the report, with the reason; a plan or spec pull request whose review failed is one of them.
   - For each worktree: `remove` → remove it; `human` → collect for the report; `local-review` → the skill's step 5, then the marker with the verdict, the round and the findings; `local-fix` → unless `exhausted`, back to the implementer with the marker's findings verbatim, as fix round `round + 1`; when `exhausted`, label the ticket `needs-human` with the skill's summary comment (what was tried, what was observed, the options) and try nothing more; `open-pr` → the skill's step 6; `push-owed` → when the ticket's `touches` name `.github/workflows/`, collect "waiting for the owner's push" with the branch and the path, and post the awaiting-push marker unless `notified`; otherwise push as the app (`… -- git -C <worktree> push -u origin <branch>`).
3. Label and unlabel `blocked` for tickets that wait for another plan's issues. Pick `Ready` tickets within the limits of the skill, none that depends on an open ticket, and start each implementer in the background, with the model of the policy and the base `origin/main`.
4. Schedule the next tick with `ScheduleWakeup`: about 5 minutes while a review or a writer runs or checks are pending; 60 minutes when only the owner's decisions and pushes remain, after one `PushNotification` (a desktop notification) that lists them, sent again only when the list changes; `stop: true` with a report at a stop condition.
5. When the session is woken by a writer's report or a finished command outside a tick, it starts a tick by invoking this command again and does nothing else first. Outside a tick the orchestrator's commands are not pre-approved; a prompt there is the safe failure.

`docs/spec/factory/README.md`: `commands/factory-run.md` in "What is in it", and the start line in "Running the orchestrator".

## Deviations from the specification

Seven departures from the process and the specification. Each is for the human maintainer to accept or refuse by reviewing this plan's pull request. The second, the third and the fourth change how a control works. The owner answered the second ("Yes, approval merges") and the third ("Accept the allowlist") on 2026-11-19; the fourth is the orchestrator's choice, which the owner can change in this review (decision log).

1. **No spec for a change that is not an initial-build milestone.** ADR-0023 and ADR-0025 put a merged `spec.md` before a plan. This plan has none and cites ADR-0023, ADR-0029, the kit README and the orchestrator skill. Why: it is factory operation with no requirement of its own, as plans 0001 and 0002 were, and far too large to be trivial.
2. **Tier high is merged by the workflow after the approval, not by the human.** ADR-0029 §4 says of tier high: "A human maintainer's approving review (check `factory/human-approval`), then the human merges or enables automatic merge"; §7 and the kit README describe `factory-automerge.yml` as enabling automatic merge "for tier low and medium". T2 and T3 arm a tier-high pull request once a human maintainer has approved its head commit, and take automatic merge off one that is not approved, paused or not. The approval requirement is not loosened, and for a plan in tier high it is tightened: T1 makes the required check `factory/human-approval` demand a maintainer's approval there too, which ADR-0029 §7 already states for the check and the kit did not do for plans. The approval is then checked twice, in two places: by the arming script, which reads the reviews itself with the policy's human check, and by that required check, computed by the gates job. What goes is the human's second step, and with it the chance to approve now and merge later, or to arm before approving. ADR-0029 is not edited; the kit README is.
3. **A permission allowlist in the guard files.** ADR-0029 §8 and the kit README checklist 7 describe the local settings as deny rules. Hard rule 1 names a "widened permission" among the things not done without a human who confirms. T11 adds thirty-four allow entries (seventeen commands in two shells) and `acceptEdits` for implementers; T14's command pre-approves the orchestrator's own commands for its turn, the review as the reviewer app among them. Why: an unattended run cannot answer a prompt. What it costs: a prompt was the moment a person saw a command before it ran; for the listed commands that moment is gone. The deny rules stay and are extended (T9, T10).
4. **The run does not end when only a human's decisions remain, and nothing is stacked.** ADR-0029 §6: "The orchestrator stops at the end of a milestone … and at any `needs-human`"; the skill's rule 12 and stop conditions end the run when "the remaining tickets are all blocked by `needs-human`, a tier-high pull request, a flagged plan, or a label only a human can apply". T13 changes that for an unattended run to: report, tell the owner, pick up nothing, keep checking. The stop at the end of a milestone is kept. ADR-0029 §5 also says "Dependent tickets are stacked"; in an unattended run they wait for the merge instead, because a stacked pull request gets no gates.
5. **One read with the person's login.** ADR-0029 §8: agents authenticate as the app, "never as the human". The pause variable is read with the owner's `gh` login, because the app cannot read it. It is a read; every write stays with the app.
6. **The owner pushes branches of agent commits that change `.github/workflows/`.** ADR-0029 §8: "Agents authenticate as GitHub App `yaf-factory` … never as the human. A person cannot approve their own pull request, so agent work must not carry a person's identity." The app has no Workflows permission, so the branch of T3, and of any later ticket that changes a workflow, reaches GitHub by the owner's push: the commits are the app's, the push event is a person's, and the pull request is still opened by the app, so the owner can still approve it. The alternative, the Workflows permission for the app, was refused (alternatives). What it costs: the owner is in the path of such a ticket at every round, and is the one who checks the workflow diff before it runs.
7. **Documentation tickets are not verified by the docs build.** ADR-0025 names the docs build for a pure documentation ticket. T13 and T15 change a skill and the root `AGENTS.md`, which are no part of the documentation site, and `dotnet docfx` cannot run before M14. They are verified by V1, V7 and V10. Also, `yaf-orchestrating-work` step 4 and ADR-0029 §6 read as if the orchestrator made the worktree; T13 gives that to the implementer's tooling, which is what the kit's `isolation: worktree` always did.
