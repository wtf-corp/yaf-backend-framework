## 1. What merges today, and what does not [repo] [live]

`.github/workflows/factory-automerge.yml` runs on `workflow_run` of `factory-gates`, when that run's conclusion is `success` and its event is not `merge_group`. It skips when `FACTORY_PAUSED` is `true`, finds the open pull request whose head is the run's `head_sha`, and then:

- labels `tier:high` or `needs-human` → "not enabling auto-merge", exit 0;
- no `tier:low` or `tier:medium` label → exit 0; a draft → exit 0;
- otherwise `gh pr merge <n> --auto --squash` with the factory app's token.

So a tier-high pull request is never armed. Live: #23 and #6 (tier high) show auto-merge enabled and were merged by the owner, who armed it by hand; #9 and #4 (tier high) were merged by the owner without it; #20 (tier low) was armed and merged by the app. The step that the owner must take after approving is real.

**The gates run again on a review.** `factory-gates.yml` has `pull_request_review: [submitted, dismissed]`. In such a run the jobs `references`, `factory-self-test` and `factory/test-evidence` are skipped (`if: github.event_name == 'pull_request'`), and `gates.mjs` reports a failing gate as a check run and still exits 0 (it calls `setCheck(…, 'failure', …)` and never `process.exit(1)`). The run's conclusion is therefore `success` after an approval, and `factory-automerge.yml` starts. That `github.event.workflow_run.head_sha` is the pull request's head commit for a `pull_request_review` run, as it is for a `pull_request` run, is **[assumed]**: the kit README lists the `workflow_run` payload under "Verify before relying on it", and T3's trial settles it.

**What holds a tier-high pull request back** [repo: research 0001 §4, the ruleset as applied]: `factory/human-approval` is a required check, pinned to `integration_id` 15368 (GitHub Actions). For a code or spec pull request `human-approval.mjs` passes it only for an approving review by a human maintainer who is not the author, given on the current head commit (`approvingHuman`, with `makeHumanCheck(policy)` from `lib.mjs`). The ruleset also requires a code owner's review on `CODEOWNERS` paths and dismisses stale reviews on a push. Auto-merge "merges a pull request automatically after all required reviews and status checks pass" [docs: https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request]. The same page: "Auto-merge is disabled if someone without write permissions pushes new changes to the head branch or switches the base branch."

**A green `factory/human-approval` is not an approval** [repo: `gates.mjs`, lines 138 and 139]. For kind `plan` the gates call `humanApprovalVerdict('low', …)` and report the check as passed, with the title "plan pull request: see factory/plan-gate", whatever the tier. A plan pull request can be tier high: by its size, a label that raises it, `major-release`, a `!` in the title. #4 and #9 were plan pull requests labelled `tier:high` [live]. And `factory/plan-gate` passes for an unflagged plan without any human. So a script that armed tier high on a green `factory/human-approval` would arm a tier-high plan nobody approved. The first version of the plan did that; the plan review found it. The arming script (T2) calls `approvingHuman` itself, for every `tier:high` pull request, and for a plan also requires a passed `factory/plan-gate`.

**The owner's decision on it, 2026-11-19 [owner]: "Require approval in the gate."** With the check green for an unapproved tier-high plan, the script would have been the only place that looked for the approval. T1 changes the gate: the call at lines 136 to 139 is `humanApprovalVerdict(kind === 'plan' ? 'low' : tier, approvingHuman(reviews, { author: pr.user.login, headSha: sha, isHuman }))`, and the title passed to `setCheck` is "plan pull request: see factory/plan-gate" for every plan. The tier handed in becomes `high` for a plan in tier high, and the fixed title is kept for the other plans only. `approvingHuman` and `humanApprovalVerdict` are pure and exported from `human-approval.mjs`, and `approvingHuman` is tested in `tests/gates.test.mjs` ("human approval: a maintainer, not the author, on the current commit"); `gates.mjs` runs as a script and cannot be imported by a test, so the new decision is a third exported function there. Neither file is in the `Touches` of any open ticket of plan 0002: its T8 (#19) changes `policy.json`, `tests/delta.test.mjs` and ten texts; its T1 (#12) changes `project.mjs`, `create-tickets.mjs`, a test and the README [repo: plan 0002, Tickets].

**A second control, in the workflow itself.** Research 0001 §6 records that disabling the ruleset for a break-glass merge released every pull request that had auto-merge armed (#3 merged unreviewed). Arming tier high on the first gates run would widen that: a tier-high pull request would sit armed while it waits. T2 therefore arms tier high only once the script has found a human's approval of the head commit, and disarms a `tier:high` or `needs-human` pull request that is armed without qualifying.

## 2. Who is told that a pull request waits [repo] [live]

- GitHub requests a review from the code owners when a pull request touches a path in `.github/CODEOWNERS`. Live: #24 (tier high, a kit path) has a request to the maintainers' team. GitHub makes that request when the pull request opens, so for a code-owned path the owner is asked before the model review has run. An approval given then cannot merge anything early: `factory/review` is a required check, so the approval only arms, and the approval counts for the commit it was given on. `GET …/requested_reviewers` returns `users` and `teams`; a pending team request is how the script sees that the code owners are already asked.
- A pull request that waits for a human and touches no code-owned path gets no request: a flagged plan (`specs/**/plan.md` is not code-owned; #9 had none), a pull request made tier high by `needs-human`, by its size, by an undeclared delta, or by `Directory.Packages.props`.
- `POST /repos/{owner}/{repo}/pulls/{pull_number}/requested_reviewers` takes `reviewers` (logins) and `team_reviewers` (slugs); it "triggers notifications"; 422 means "Unprocessable Entity if user is not a collaborator"; "Once a requested reviewer submits a review, they are no longer considered a requested reviewer" [docs: https://docs.github.com/en/rest/pulls/review-requests, API version 2022-11-28]. The page names no app permission; Pull requests write is **[assumed]** to be enough for a user reviewer. A team reviewer may need more; the call's failure is a warning.
- **Where the request is made.** A review request is not among the `pull_request` types that start `factory-gates.yml`. More important: nothing starts a gates run when a review check is reported, so `gates.mjs` cannot ask "after the model review has passed". `post-review.mjs` runs at exactly that moment, in both modes: locally as the reviewer app, which has Pull requests write (research 0002 §1), in CI in a job with `pull-requests: write`. It has the policy, the changed files (fetched) and `heldForHuman`; from the event it has only what `local-review.mjs` writes there, `{ pull_request: { number, base: { sha }, head: { sha } } }`, so the labels, the requested reviewers and the reviews are fetched through the API by T4; the label `tier:high` is on the pull request because the gates run before the review (`AGENTS.md`, "Model reviews run locally": "once the gates have run"). `local-review.mjs` runs the poster of the base branch, so T4 takes effect for pull requests reviewed after it has merged.
- `policy.json` `humans.logins` is filled here; `makeHumanCheck` uses the list alone when it is. The request goes to those logins, or to `humans.team` when the list is empty.

## 3. How a failed review is found, and how rounds are counted [repo]

`post-review.mjs`, run by `local-review.mjs` (and by the CI workflows when they are on):

- writes one summary comment per check on the pull request, found again by the marker `<!-- factory:review-summary factory/review -->` (or `… factory/doc-review -->`), and updates it in place. The comment holds the verdict, the pass table and every finding with file, line, what and suggested fix;
- keeps the count in the comment: `<!-- factory:rounds=N -->`. `N` goes up by one on every failed review and stays on a pass;
- applies `needs-human` when a review fails and `N > limits.fixRounds + 1`: the first failed review plus `fixRounds` fix attempts;
- reports the check run `factory/review` or `factory/doc-review` on the head commit, with the summary as its output.

`local-review.mjs` also reports the other review check as passed ("not applicable"); `gates.mjs` does the same in CI. So on a head commit that has been reviewed both names are present, and the review that is still owed is the name that is missing.

What follows for the loop: a failed review with `N = 1` is fix round 1 of 2, `N = 2` is round 2 of 2, and at `N = 3` the label is already there and nothing more is tried. A push gives a new head commit with no review check: the review is owed again (`AGENTS.md`, "Model reviews run locally": "after it opens a pull request and after every push to one, once the gates have run"). The findings to pass on verbatim are the body of the summary comment.

**A running review cannot be seen today.** Between the start of `local-review.mjs` and the poster, about three minutes, the head commit has no review check: the same state as "review owed". A check run can be created with `status: in_progress` and `started_at`; "To create a check run, you must use a GitHub App"; `conclusion` is "Required if you provide completed_at or a status of completed" [docs: https://docs.github.com/en/rest/checks/runs, "Create a check run"]. The reviewer app has Checks write. `lib.mjs` `setCheck` always sends `status: completed`, so T12 adds a function next to it that builds the body, and `local-review.mjs`, which already imports `setCheck` from the base checkout's `lib.mjs`, imports that one the same way. `lib.mjs` is in no open ticket of plan 0002. The kit assumes that the newest check run of a name decides (kit README, "Verify before relying on it"); the completed run the poster reports is newer than the one in progress.

**No script can tell who the reviewer is.** `policy.json` `bots` holds `factory` (`yaf-factory[bot]`) and `gates` (`github-actions[bot]`); `policy.schema.json` gives `bots` exactly those two properties, both required, with `additionalProperties: false`. The reviewer app's name is in a comment of `local-review.mjs` ("the reviewer app (yaf-reviewer: …") and in `AGENTS.md`, and its login is `yaf-reviewer[bot]` (research 0002 §1). The summary comment is written by that app when the review runs locally and by the gates bot's token when it runs in CI. Who reads `bots` today: `gates.mjs` reads `bots.gates` twice; `digest.mjs` takes a list of bots as a parameter; no test reads a key of `bots` [repo: searched the kit for "bots"]. So an optional third key breaks nothing, and the schema must name it.

**What only the session knows today.** The local code review's verdict, its round and its findings, and "the owner was told", are in the orchestrator's conversation and nowhere else; a restarted run could neither hand the findings to an implementer nor tell that the two rounds of `limits.fixRounds` were used. `post-review.mjs` shows the pattern for a record on GitHub: a hidden marker in a comment, found again by its text. Issue comments are written through `gh issue comment` as the factory app (Issues write).

`project.mjs` `statuses()` and `status.mjs` exist for the Project; nothing in the kit reads the state of open pull requests or of finished worktrees for the orchestrator. T5 to T8 add it.

**Jobs of the gates workflow that are no `factory/*` check.** `references`, `factory-self-test` and `factory/test-evidence` are jobs of `factory-gates.yml` and show as check runs of those names on the head commit [live: #24's checks]. `references` is a required check; the other two are not. A failed `references` has a mechanical fix: `node .github/scripts/sync-references.mjs` writes the references, and the result is committed.

**The writers of plans and specs are not isolated.** The `planner` and `spec-writer` definitions have no `isolation: worktree` and no `permissionMode` [repo: their front matter; the kit README's table of agents]; only the two implementer definitions have the first, and T11 gives only them `acceptEdits`. A fix round by one of them inside an unattended run would edit the main checkout, where the orchestrator sits, and stop at the first edit prompt.

**Stacked pull requests get no gates.** `factory-gates.yml` has `pull_request: branches: [main, next]`: a pull request whose base is another ticket's branch starts no run [repo]. So in an unattended run every pull request targets `main`, and a dependent ticket waits for the merge.

## 4. Strict status checks, and the owner's decision [repo] [owner]

As applied and recorded in research 0001 §4, the ruleset of `main` has `strict_required_status_checks_policy: true` and no merge queue. With it, every merge puts every other open pull request behind `main`; auto-merge does not update a branch; an update (`gh pr update-branch`, a merge of the base branch into the head, gh 2.102.0) is a push, so the gates run again, the model review is owed again, and an approval is dismissed (`dismiss_stale_reviews_on_push: true`; `factory/human-approval` counts only an approval of the head commit). With several tier-high pull requests open, each merge would cost the others a review each and the owner a second approval each.

**The owner's decision of 2026-11-19 [owner]: "Strict off until M0 has CI."** The owner unticks "require branches to be up to date before merging" in the ruleset now, and turns it back on, or adds a merge queue (`18` §4, "Merge queue"), once `ci.yml` builds and tests something. It is a change only the owner makes and is a precondition of the plan, not a ticket. The plan therefore builds nothing for a branch that is behind; what to do then is an open point for M0's plan.

**Plan 0001's files.** `specs/0001-factory-setup-runbook/research.md` §4 states the strict policy as applied ("`required_status_checks`, strict", and `"strict_required_status_checks_policy": true` in the ruleset shown), and 0001's runbook is written from it. `specs/0001-factory-setup-runbook/plan.md` does not mention it [repo: searched for "strict" and "up to date"]. Both files are merged; this plan does not edit them. Research 0001 §4 needs a plan update of its own, saying that the policy is off from 2026-11-19 until M0 has a build.

## 5. Claude Code: scheduled runs [docs]

Source: https://code.claude.com/docs/en/scheduled-tasks, read on 2026-11-19.

- `/loop <prompt>` with no interval: "Claude chooses one dynamically … After each iteration it picks a delay between one minute and one hour based on what it observed". "You can also pass a skill as the prompt, for example `/loop 20m /review-pr 1234`, to re-run that skill each iteration."
- "A scheduled fire only runs skills that Claude is allowed to invoke on its own." A skill marked `disable-model-invocation: true` reaches Claude as plain text instead. The entry point must therefore not carry that field.
- "A scheduled prompt fires between your turns, not while Claude is mid-response." "No catch-up for missed fires."
- "Tasks only fire while Claude Code is running and idle. Closing the terminal or letting the session exit stops them firing." A self-paced `/loop` "isn't restored" by `--resume` or `--continue`: "run `/loop` again to restart it."
- "Recurring tasks automatically expire 7 days after creation"; "The seven-day expiry applies to the loop too."
- Stopping: "while the loop is waiting for its next iteration, press `Esc` on an empty prompt". Claude ends a self-paced loop by calling `ScheduleWakeup` with `stop: true`. "If an iteration ends without either rescheduling or stopping, Claude Code schedules one fallback wakeup about 20 minutes later and ends the loop when that iteration doesn't reschedule either."
- `.claude/loop.md` replaces the built-in prompt of a bare `/loop`. Not used: it takes no front matter (section 7).
- Tools [docs: https://code.claude.com/docs/en/tools-reference]: `ScheduleWakeup` "Reschedules the next iteration of a self-paced `/loop` … between one minute and one hour out"; `PushNotification` "Sends a desktop notification from a local session, and a phone push with Remote Control", permission required: no; `SendMessage` resumes a subagent "by agent ID or name".

## 6. Claude Code: worktrees and subagents [docs] [observed] [repo]

- A subagent with `isolation: worktree` runs "in a temporary git worktree"; worktrees are created "under `.claude/worktrees/`", branched "from your repository's default branch unless `worktree.baseRef` is set to `\"head\"`"; "You can't set `worktree.baseRef` to a branch name."

To remove by hand: `git worktree unlock`, then `git worktree remove`.
- **Observed:** an implementer's harness refuses git operations aimed at another worktree ("a worktree-isolated agent's git operations must target its own worktree"). The docs list the checks: file edits in the main checkout, a command whose working directory resolves to the main checkout, git redirected there by `git -C`, `--git-dir`, `GIT_DIR` or a `cd`.

For #17 the implementer committed on `worktree-agent-<id>`, and the orchestrator fast-forwarded the ticket branch to that commit and removed the agent's worktree **[observed]**. Three such hand-made worktrees exist today (`ci-12-…`, `ci-13-…`, `ci-17-…`) [repo].
- **What already fits.** The `implementer` definition, "How", step 1: "Create the branch `<type>/<issue>-<slug>`", and its inputs name "The branch to create and what to base it on". An implementer may switch branches inside its own worktree; the docs' cleanup rules name the case ("Another branch is checked out"). A stacked ticket needs a base that `worktree.baseRef` cannot give, and `git switch -c <branch> origin/<base>` in the implementer's own worktree can.
- **Cleanup.** "Each subagent gets a temporary worktree that Claude Code removes automatically when the subagent finishes without changes; a worktree with changes stays on disk" until a sweep, which leaves a worktree that "still holds work: changed or untracked files, or unpushed commits".
- **Resuming.** "Claude uses the `SendMessage` tool with the agent's ID or name as the `to` field to resume it"; "Resumed subagents retain their full conversation history". Whether a resumed implementer finds its worktree again is not stated: **[assumed]**, and the plan gives a second route that does not depend on it.
- **Background subagents** "surface every permission prompt in your main session". A subagent "inherits the main conversation's permission mode" unless `permissionMode` is set in its front matter, which is honoured "When the main conversation is in `default` or `dontAsk` mode". The built-in subagents each inherit "the parent conversation's permission rules"; that custom subagents do too is **[assumed]** (the kit README lists "The deny rules of `.claude/settings.json` apply to subagents" as unverified).
- The model: "The per-invocation `model` parameter, which Claude can pass when it starts the subagent" comes first. This settles the kit README's open point on the model override, by the documentation.

## 7. Claude Code: permission rules [docs] [observed]

Source: https://code.claude.com/docs/en/permissions, read on 2026-11-19; research 0002 §3 holds what was established before and is not repeated.

- **PowerShell has rules of its own.** "PowerShell permission rules use the same shape as Bash rules"; matching is case-insensitive; aliases are canonicalised; each command of a compound command is checked. A `Bash(...)` rule does not cover the PowerShell tool. **Observed** in the local code review of 0002's T6 (#17): every `gh`, `git`, `dotnet` and `npx` deny rule of `docs/spec/factory/.claude/settings.json` is `Bash(...)`. On `main` at `f8240f5`, with 0002's T6 merged as #24, the list holds 38 rules: 37 `Bash` and one `Read` [repo: counted on 2026-11-20], so on Windows the same command through the PowerShell tool is not denied. This machine's primary shell is PowerShell.
- **`Read` rules are path rules.** "Claude makes a best-effort attempt to apply `Read(path)` deny rules to all built-in tools that read files"; "On Windows, paths are normalized to POSIX form before matching" (research 0002 §3). For Bash commands the page names the file commands and redirect targets it recognises. It does not say the same of PowerShell commands: whether `Get-Content` of a denied path is stopped is **[assumed] not**. T6 of 0002's `Read(~/.wtf-corp/yaf-factory/**)` needs no twin; its limit is in research 0002 §3.
- **Allow rules.** "A `*` can go anywhere in the rule"; `Bash(ls *)` matches `ls -la` and `ls`, not `lsof`. "Every subcommand must be allowed for a compound command to run without a prompt." "Rules are evaluated in order: deny, then ask, then allow." A rule that tries to constrain arguments is "fragile". Wrappers `timeout`, `time`, `nice`, `nohup`, `stdbuf` are stripped before matching.
- **A rule matches the command text.** `Bash(gh pr merge *)` does not match `node .github/scripts/factory-token.mjs --app factory -- gh pr merge 5`: the text starts with `node`. After plan 0002 every `gh` and `git` command of the factory goes through the helper, so the 34 `gh` and `git` deny rules no longer match the form agents are told to use [repo: the rules; plan 0002, T7]. The plan closes this in the helper, by argument and not by text (T9).
- **Project allow rules need trust.** "`permissions.allow` rules … in a project's `.claude/settings.json` grant capability, so Claude Code applies them only after you accept the workspace trust dialog for that folder"; "In a worktree, it uses the main checkout's root."
- **Where settings load in a worktree.** `.claude/settings.json` loads "from the current working directory's `.claude/` folder", so a worktree reads its own checked-out copy, which is the committed file. `.claude/settings.local.json` is shared with worktrees through the main checkout, "except … on Windows", where a saved rule "stays with that worktree". So guidance for `settings.local.json` would not reach an implementer's worktree on this machine; the committed file does.
- **Modes.** `acceptEdits` "Automatically accepts file edits and common filesystem commands such as `mkdir`, `touch`, `mv`, and `cp` for paths in the working directory". `permissions.denyInsteadOfPrompting`, "in your user or managed settings", denies "calls that would wait on a permission prompt, so an unattended session keeps working".
- **A grant for one turn.** Skill and command front matter `allowed-tools` "grants permission for the listed tools during the turn that invokes the skill … The grant clears when you send your next message … invoking the skill again re-applies it for that turn"; "Your existing `.claude/commands/` files keep working" [docs: https://code.claude.com/docs/en/skills]. Whether the grant reaches subagents started in that turn, and whether it holds in a turn started by a subagent's report instead of by the command, is **[assumed] not**. The plan is written so that the failure is a prompt, never a wider grant.
