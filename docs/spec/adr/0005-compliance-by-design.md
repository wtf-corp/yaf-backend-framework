# ADR-0005 — Compliance by design

> **Status** Accepted
> **Date** 2026-11
> **Deciders** Framework maintainers

## Context

Applications built on YAF operate under regimes such as ISO/IEC 27001, GDPR, NIS2 and, when they use AI, the EU AI Act. Many of their requirements are organisational, but a substantial part can be implemented or enforced by code: access control, encryption, logging, retention, erasure, data inventories, change control. When each application implements these separately they are implemented late, inconsistently, and without evidence.

A framework can provide these controls once. It can also do harm by overclaiming: a library cannot make an organisation compliant, and saying so misleads its users.

## Drivers

- Controls that code can enforce are present by default, not retrofitted.
- Each control is traceable to the requirement it supports and to tests that prove it works.
- Evidence is generated by the build, so it cannot drift from the code.
- Claims are limited to what the framework actually does.
- The catalogue must be maintainable as regulations change.

## Options considered

| Option | For | Against |
|---|---|---|
| Leave compliance to each application | No framework effort | Repeated, inconsistent, late; no shared evidence |
| Ship the request-handling processes (coordinator, incident register) in the core packages from the first release | Complete out of the box | A business domain inside a framework that has none; large scope before the mechanisms are proven |
| Ship features (encryption, audit) and describe them in prose | Simple | No traceability; documentation drifts; no proof |
| **A control catalogue kept as code: control id → mechanism → tagged tests → generated evidence** | Traceable, verifiable, reviewable in diffs | Catalogue and tags must be maintained |
| Adopt a compliance product or external GRC tooling as the source | Rich reporting | External to the code; does not enforce anything |

## Decision

### Position

YAF implements the controls that code can enforce and produces evidence that they work. It does **not** make an application compliant, and nothing in the framework, its documentation, its comments or its generated reports says that it does.

### Sources

Primary: ISO/IEC 27001:2022 Annex A, GDPR (Regulation 2016/679), NIS2 (Directive 2022/2555, with Implementing Regulation 2024/2690 as a benchmark), the EU AI Act (Regulation 2024/1689 as amended).

Supporting catalogues used to derive concrete checks: OWASP ASVS 5.0, OWASP API Security Top 10, OWASP Top 10 for LLM applications, NIST SSDF, SLSA, the Cyber Resilience Act, DORA, SOC 2, PCI DSS.

**Caveat.** The clause identifiers in `spec/11-privacy-and-compliance.md` §8 were compiled in November 2026, some from secondary copies. Each identifier must be verified against the official text before `docs/compliance/` is published, and re-verified when a source is amended. An identifier that cannot be verified is removed, not guessed.

### The control-catalogue method

1. A control has a YAF id (`C-AC-1`, `C-DP-5`, `S3`…), a one-line requirement, the mechanism that implements it, and the source clauses it **supports**.
2. Tests that prove the control carry `[Control("C-AC-1")]`.
3. A CI tool (`yaf-compliance`) reads the catalogue and the test results and generates `docs/compliance/controls.md`: control → requirement → mechanism → tests → result of the last run.
4. A control without a passing test fails the build. A test tag naming an unknown control fails the build.
5. The catalogue lives in the repository as data; adding, changing or removing a control is a reviewed change that cites this ADR or a later one.

Control families: access control (AC), cryptography (CR), data protection (DP), logging and records (LG), configuration (CF), secure development (SD), supply chain (SC), resilience (RS), incidents (IN), plus the security tenets S1–S10 (ADR-0004). The AI family (AI) arrives with the later `YAF.AI` package (ADR-0022).

### Scope of the first release

1.0 ships the mechanisms: classification, redaction, retention and purge, legal hold, subject keys and crypto-shredding, generated exporters and erasers per context behind `IDataSubjectOperations`, processing restrictions, and the inventory and control-matrix tooling. Their storage is mapped by `YAF.Privacy.EfCore`. The privacy coordinator bounded context (data subject request aggregate, deadlines, orchestration across services), the incident register and `DecisionRecord` are planned for a later release; they are processes built on these mechanisms, and keeping them out of the first release keeps the core free of a business domain of its own.

### Generated evidence

| Artefact | Supports |
|---|---|
| `data-inventory.md` / `.json`: type → member → classification, category, purpose, storage treatment (including every member stored in clear and its reason), retention, erasure action, which integration events carry it | Input to records of processing and impact assessments |
| `controls.md` | Accountability, audit preparation |
| `authorization-inventory.md` | Access control review |
| `error-catalogue.md`, `configuration-reference.md`, `unsafe-options.md` | Change and configuration management |
| SBOM and provenance per release | Supply chain |

A change that alters any of these shows as a diff in the pull request.

### Build time versus run time

| Enforced at build time | Enforced at run time |
|---|---|
| Authorization markers present (C-AC-1) | Authentication and authorization decisions |
| Every persisted or transmitted member classified (C-DP-1) | Tenant filters and row-level security |
| No personal data in events or jobs without justification (C-DP-3) | Field encryption, key rotation, subject-key shredding |
| Retention policy present on every personal-data type (C-DP-4) | Redaction in every sink |
| Exporter and eraser exist for every data-subject-owned type | Audit trail writing, sealing and chain verification |
| Clock and weak-crypto APIs banned (C-LG-4, C-SD-1) | Retention purge, partition drop after checkpoint |
| Layering, vendor isolation, no test doubles in production | Restriction and objection checks |
| Locked, audited dependencies (C-SC-1) | Security events |
| Generated artefacts in sync | Startup guards, including purposes checked against the catalogue |

### What must never be claimed

- That YAF, or an app built on it, is "GDPR / NIS2 / ISO 27001 / SOC 2 / AI Act compliant" or "certified". Organisations and scoped management systems are assessed, not libraries.
- That the framework decides lawful basis or purposes, performs an impact assessment, *is* the record of processing, or decides whether an incident is notifiable. It supplies inputs and timers.
- That crypto-shredding is formally recognised erasure (ADR-0011), or that the audit trail is tamper-proof. It is tamper-evident, given a protected anchor, and the newest rows are chained shortly after commit, not at commit.
- That logs, events, stamps or audit columns are free of personal data. They hold no directly identifying data; the user ids and keyed hashes in them are pseudonymous personal data, bounded by the retention of those stores.
- That classification guarantees no leakage. It is as complete as the annotations; free text defeats it.
- That an approval record is human oversight in the regulatory sense, or that the framework makes a model accurate or unbiased (ADR-0022).
- Anything about organisational or infrastructural controls: backups and restore tests, network segmentation, MFA enrolment, key custody, training, supplier contracts, penetration tests, incident notification to authorities.

The compliance page of the docs site opens with this list. Permitted wording: "supports", "implements a control for", "provides evidence for".

## Consequences

**Positive**

- Privacy and security controls exist from the first commit of a service, with tests.
- An auditor or a customer questionnaire can be answered from generated files.
- Regulation changes map to catalogue rows, and from there to code and tests.
- Honest scope: users know which obligations remain theirs.

**Negative / costs**

- Every member needs classification, every personal-data type a retention policy and erasure action. This is deliberate friction.
- The catalogue, the tags and the identifiers need upkeep; legal texts must be re-read when amended.
- Encryption of personal data by default removes sorting, range and substring search on those members. `[StoredInClear("reason")]` gives them back per member, at the price of weaker protection for that member and a visible entry in the inventory.
- In 1.0 an app must build the handling of a data subject request (intake, verification, deadline, collecting results across services) itself, on top of `IDataSubjectOperations`.
- User ids and keyed hashes in logs, stamps, audit columns, envelopes and job rows are not reached by erasure; the controller must assess them against the retention periods.
- The risk of being read as a compliance guarantee remains and must be countered in every public text.

## Enforcement

| Mechanism | What it checks |
|---|---|
| Analyzers `YAF2001`–`YAF2008` | Classification present and placed on properties; retention present; personal data in events justified; secrets refused in payloads; declared free-text members justified; no classified value in exceptions or logs; `[StoredInClear]` refused on sensitive and secret members |
| Startup check and template test | Every purpose used in an attribute is in `IPurposeCatalog` |
| Architecture tests | Every data-subject-owned type has an exporter and an eraser; every personal-data type lists a retention policy; every tenant table has a row-level security policy |
| `yaf-compliance` in CI | Every control has at least one passing tagged test; no unknown tags; generated files equal the committed ones |
| Docs lint | The words "compliant", "certified", "tamper-proof", "guarantees" in `docs/`, XML comments and READMEs fail the build unless on an allow-listed line (the "never claimed" list itself) |
| Integration tests in the reference sample | Export, erasure with key destruction and chain still verifying, legal hold, retention purge with evidence, partition drop after checkpoint, restriction |
| Pull request template and review checklist | "Touches personal data: classification / retention / erasure action / inventory updated"; "free-text members carry `[FreeText]`" |

## Guidance for agents

- A change that adds or alters a member holding personal data updates, **in the same pull request**: its classification (with category and purpose), the type's retention policy, the member's erasure action, the data-subject marker, and the regenerated inventory. An inventory diff you did not expect means you leaked data into a new place; investigate before committing it.
- Never put personal data into an integration event, a job payload or process state to save a lookup. Send the id. `[AllowPersonalData]` needs a reason taken from the spec.
- Never write `Keep` as an erasure action, or `[StoredInClear]` on a personal member, without the reason given by a human in the spec.
- Mark a member that holds text typed by a user `[FreeText]`. The analyzer cannot find these for you.
- Never write that logs, events or audit columns "contain no personal data". Say "no directly identifying data".
- When you add a control or change how one works, add or update the `[Control]`-tagged test and the catalogue row together.
- Never write that YAF or an application is compliant, certified or guaranteed secure, in docs, comments, commit messages, README files or generated reports. Use "supports" or "implements a control for".
- Never invent or "correct" a clause identifier from memory. If you cannot check it against the official text, mark it unverified and say so.
- Never lower a retention floor, disable the purge job, the audit trail or redaction, or exclude a type from the inventory, without a spec that names the change.
- Tests use synthetic data from the builders in `YAF.Testing`. Never copy real personal data into a test, a fixture or an example.
- If a requirement seems to need a legal judgment (lawful basis, whether data is personal, how long to keep it), stop and ask. That decision is a human's.
